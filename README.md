## Message Queue & Event Streaming

Event-driven architecture is central to how I build scalable backends. I use message queues to decouple services, handle async workloads, and build resilient pipelines that recover gracefully from failures.

```
PRODUCERS                    BROKER                    CONSUMERS
─────────────────────────────────────────────────────────────────
Order Service   ──┐
                  │      ┌──────────────────┐    ┌── Email Worker
User Service    ──┼─────▶│  RabbitMQ/Kafka  │────┤
                  │      │  Exchange/Topics  │    ├── Notification
Payment Service ──┘      │  Dead-Letter Q   │    │
                         └──────────────────┘    └── Analytics
                                                      Pipeline

  Patterns: Work Queues · Pub/Sub · Topic Routing · RPC
  Guarantees: At-least-once · Idempotent consumers
  Retry: Exponential backoff · DLQ · Poison message handling
```

**Key practices:**
- Idempotent consumers to safely handle duplicate messages
- Dead-letter queues for failed message inspection and replay
- Schema-validated payloads (Pydantic / Avro / Protobuf)
- Horizontal scaling of consumers based on queue depth

## Principles

> *Build systems that are simple to reason about, resilient by default, and easy to operate at 3 AM.*

- Prefer boring technology for critical paths; innovate at the edges
- Design for failure — circuit breakers, retries, and graceful degradation
- Observability is not optional: logs, metrics, and traces from day one
